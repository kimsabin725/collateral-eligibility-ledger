# 후보 A — Look-Through Entitlement Register
### "등록부는 풀 안을 보지 못한다"

## A-1. 문제

증권형 토큰이 볼트·풀·렌딩 담보 컨트랙트로 들어가는 순간, 발행사의 법적 명부가 인식하는 보유자는
**그 컨트랙트 주소**다. 배당·의결권·원천징수·수익적 소유 보고가 전부 record date의 "보유자"에
걸려 있는데, 그 보유자가 사람이 아니다.

## A-4. Attestcoin 적합성 — **부분적** ⚠️

대상이 *포지션*이라 proof 모델과 어긋난다. 완전성(부재 증명)이 불가능하므로 "정본 명부"는 만들 수 없고,
**청구 기반 구조**만 건전하다:

1. 투자자가 자기 예치·인출 tx를 proof로 제출 → `provenPosition = Σ입금 − Σ출금`
2. 누구나 더 나중의 출금 tx를 증명해 청구를 자동 감액 (은닉 공격 차단)
3. **보존식:** Σ지급가능청구 ≤ 증명된 풀 보유량
4. 레지스터는 "완전한 명부"가 아니라 **"반증되지 않은 증명된 청구"**만 주장

## A-5. 치명적 반론

1. **[FACT]** 시장 지배적 발행 인프라(Securitize)가 **정확히 이 이름으로** 대응 중 → patchability 테스트 통과 곤란
2. "발행사가 허용한 볼트만 쓰게 하면 그만" — 실제 방향이 그렇다
3. 발행사가 Registrar를 붙이면 투자자 단위 추적이 회복된다

## A-6. 살아남는 좁은 각도 (선택 시 라운드2 과제)

> **투자자가 관리자(transfer agent)를 신뢰하지 않고 스스로 자기 지분을 증명하는 경로.**
> Vault Registrar는 *기록의 품질*을 올리지만, 투자자는 여전히 Securitize의 오프체인 행정을 신뢰해야 한다.
> "당신 장부가 틀렸다"를 투자자가 **증명으로** 말할 수 있는가 — 이것만 남는다.

# 후보 B — Issuer Control Action vs DeFi 담보
### "발행사가 법적 의무로 담보를 발밑에서 빼간다"

## B-1. 문제

규제 증권 토큰에는 발행사(또는 규제기관 명령)에 의한 **freeze / forced transfer / clawback**이
표준 기능으로 들어 있다. 그 토큰이 다른 곳에서 **담보로 잡혀 있는 동안** 그 권한이 행사되면:

- 대주(lender)의 담보가 동결되거나 제3자에게 강제 이전된다
- 프로토콜의 리스크 엔진은 이 사실을 **알지 못한 채** 정상 담보로 계속 계산한다
- 청산을 시도해도 이전 자체가 거부될 수 있다

**두 개의 정당한 권한이 같은 자산 위에서 충돌한다.** 발행사는 법적 의무를 이행한 것이고,
프로토콜은 코드대로 동작한 것이다. 어느 쪽도 버그가 아니다.

## B-2. 왜 patchable하지 않은가

| 검사 항목 | 판정 |
|---|---|
| 한 프로토콜의 기능 추가로 사라지는가 | **아니오** — 발행사는 Aave/Euler/Morpho를 패치할 권한이 없고, 프로토콜은 발행사의 법적 통제권을 없앨 수 없다 |
| 서로 다른 법적 주체가 필요한가 | **예** — 발행사(규제 대상)·프로토콜(무허가 코드)·대주 |
| DeFi 때문에 새로 생기는가 | **예** — TradFi에서는 담보권자가 수탁자를 통해 통지받는다. 무허가 담보에는 그 통지 경로가 없다 |

## B-3. Attestcoin 적합성 — **높음** ✅

대상이 **이산 사건**이다. freeze/forced transfer는 트랜잭션 하나로 일어나고, 그것이 정확히
Attestcoin이 증명할 수 있는 형태다. 잔액 재구성도, 완전성 가정도 필요 없다.

**어제 만든 엔진이 그대로 재사용된다:**

```
어제:  SetIsAllocator(X)@A  →  ReallocateSupply(X)@B>A     (권한 → 행위)
오늘:  IssuerControlAction(token,holder)@A  →  담보 상태/행위@B  (통제 → 영향)
```

동일한 5중 검사(proof 검증 → receipt status → emitter allowlist → event signature → replay 방지)와
동일한 엄격한 블록 순서 판정이 그대로 적용된다.

## B-4. PoC 설계 초안

| 구성 | 위치 | 내용 |
|---|---|---|
| 사실 A | **Ethereum mainnet (실제)** | 실제 규제 토큰의 발행사 통제 이벤트 |
| 사실 B | **Sepolia (mock)** | 우리가 배포한 mock 렌딩 시장에 담보 예치 |
| 판정 | **Creditcoin CC3** | `CollateralIntegrityLedger` — 증명된 통제 사건을 admit하고, 영향받는 담보 포지션을 **impaired**로 표시 + 사건 이전/이후 순서 판정 |

**실패 시연:** 통제 사건이 증명되지 않은 세계에서는 담보가 정상으로 표시되고 대출이 계속된다 →
같은 사건을 proof로 admit하면 즉시 impaired로 뒤집힌다. 8~9분 지연은 "감사·사후검증" 포지셔닝과 부합.

## B-5. 치명적 반론 (미해소)

1. **permissioned 시장에서는 발행사와 프로토콜이 오프체인으로 조율할 유인이 크다** — 실제로 Horizon은
   발행사가 화이트리스트를 통제한다. "그냥 서로 전화하면 되는 문제" 반론이 가장 강하다.
2. 프로토콜이 발행사 컨트랙트를 직접 구독하면(같은 체인이면) Attestcoin 없이 해결된다
   → **cross-chain일 때만 load-bearing**이라는 점을 서사의 중심에 둬야 한다.
3. 8~9분 지연 때문에 **실시간 차단은 불가능** — "사전 방어"가 아니라 "검증 가능한 사후 기록"으로만 주장 가능.

## B-6. [UNVERIFIED] 즉시 확인해야 할 것 — B를 고르면 첫 작업

1. **실제 메인넷에 발행사 통제 이벤트가 존재하는가?** BUIDL(DS Protocol)·USTB(Permissionlist)·
   ERC-3643 계열의 실제 event signature와 실제 발생 사례를 온체인에서 찾아야 한다.
   **없으면 B의 "실제 데이터" 강점이 사라진다.**
2. 그런 사건이 실제로 담보로 잡힌 토큰에 일어난 사례가 있는가
3. Hypernative 등 모니터링 업체가 이미 커버하는 범위
