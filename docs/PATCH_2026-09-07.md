# 사건 순서 및 위험 재발 패치 — 2026-09-07

## 수정

- 최초 훼손 블록은 이력용으로 보존하고 현재 상태와 분리했다.
- 현재 상태는 증명된 소스 위치(블록, 트랜잭션 인덱스, 영수증 로그 인덱스)가 가장 나중인 사건으로 결정한다.
- 훼손 → 복구 → 재훼손에서 신규 여신이 다시 차단된다.
- 먼저 수신한 복구 증명도 보존한다. 복구만 있으면 NO_PROOF이며, 훼손도 증명되면 사건 순서에 따라 상태를 결정한다.
- 기존 자산의 소스 체인 변경을 거절해 다른 체인의 사건 이력이 섞이지 않도록 했다.
- latestEvents 조회를 추가했다. 기존 Asset 조회 및 submitEvent 입력 형식은 유지했다.
- restoredAt은 최신 증명 복구 블록이며 현재 상태 판정에는 statusOf를 사용해야 한다.
- Restored 이벤트는 복구 사건이 최신으로 수신되었다는 뜻이다. 복구만 증명된 경우 statusOf는 NO_PROOF이므로 소비자는 이벤트만으로 여신을 허용하면 안 된다.

**재배포 완료.** CC3 테스트넷(chainId 102031)에 패치본을 배포하고, 실제 sNUSD pause 증명을 재입력했다.

```

GatedCreditLine    0xDcd5dfb82CA8fcDD3E628b327d5CeaCdBE69771A
EvmV1Decoder       0x00718d01897236C3352D5BA689BcC5c540dd9d97

```

온체인 확인: `statusOf` NO_PROOF → **IMPAIRED**, `impairedSince` 25,745,732(소스 블록),
`openPosition` **AssetImpaired**로 리버트 — 신규 여신 차단 확인.
배포 이후 라이브 주소에 대해 읽기 전용으로 다시 조회한 기록이 `docs/transcripts/verify-cc3-2026-09-07.log`에 있다
(`contracts/`에서 `node scripts/verify-deployment.js`로 재현). 데모 영상이 패치 전 배포를 보여주므로 이 기록이 보완 자료다.

**디코더는 재사용 가능하다.** 패치는 디코더를 건드리지 않았고, 구 배포 `0xd735522d27cF22E443F48a3a3A3Dd2de8f24F008`과
신 배포 `0x00718d01897236C3352D5BA689BcC5c540dd9d97`의 온체인 런타임 코드가 10,272바이트로 바이트 단위까지 같다.
새 원장을 구 디코더에 물려도 동작이 같다. 패치본 세트를 자체 완결로 두려고 새로 배포했을 뿐이다.
배포 지갑은 8월과 동일하며 프록시가 아니므로 **8월 배포의 사건 이력은 이전되지 않았다.**
패치 전 배포(`0xA47a20079112252afAF2d54fF1FF0268bE3826a4` 등)는 온체인에 그대로 남아 있고, 데모 영상이 보여주는 것이 그 배포다.
덱(`docs/deck.html`/`deck.pdf`)은 2026-09-07에 새 주소로 갱신했고, 영상이 이전 배포로 녹화됐다는 각주를 넣었다.
